# 执行者的取舍

一件活可以交给四类执行者：脚本、判定模型、直接调用的 LLM API、harness。运行环境里有哪些入口、价格与限流，查那里的调用文档。

## 脚本

该不该用循常驻原则 §4。这里的推导，是说清规则、适用前提与任务定义之间的关系，通常一句可核对的理由就够，不靠"在见过的样例上都对"：任务定义是数不同的患者 ID，按该字段去重计数对没见过的 ID 同样成立；码表内的代码即使头一次出现也按表归类，表外的代码按约定报为未知。推导不出的不由脚本裁决：判读自由文本时，关键词或正则的命中可以当证据，结论仍取决于语境的，由模型依据材料判断；判定标准本身还没定的，循常驻原则 §3。

推导成立之后，仍要核验实现确实照这条规则做，并检查当前输入的关键前提。对失效后会产出看似有效结果的前提，能从输入检查的就检查；检查不过时标明受影响的记录或任务，不采用相应结果。字段含义这类从输入判定不了的关键前提，先查来源或规范；仍确认不了的标为未决。

## 判定模型

在固定选项里判定，只返回标签、分数或概率，不生成文字。

- 单条通常比生成式调用快、便宜，适合大批量的分类、初筛和当参考信号。
- 不给理由，单例判错从输出里看不出原因，准不准随任务变。新用法先拿有代表性的已标注样本验证；关键判断另有证据支撑。
- 阈值按任务目标定，换模型后重新验证；下游要把输出当概率解释时，另查概率校准。

## 直接调用 LLM API

适合材料能事先备齐、一次判断或生成就够的活；结论可以附理由供人审查。

- 没有 harness 的系统提示和工具循环，输入全是任务本身：开销小，行为更可控。
- 材料由调用方备齐，影响任务的参数由调用方设。调用成功不等于结果可用：回包可能答案为空、被上限截断、要求的参数没生效，或模型与请求不符，看起来都和正常结果一样。所以逐条核对最终答案是否完整可用，并按接口文档核对回包里看得到的结束原因、模型标识和用量；要求的配置从回包核实不了的，标为未核实。空答案和截断的结果单列，处理后才并入结果集。
- 接口支持前缀缓存时，把固定内容（指令、标准、共享材料）放在逐条变化的内容之前；命中多少按接口给的统计核对。

## harness

模型自己取材、调用工具、多轮动手；适合要根据中间结果继续取材或行动的活。sub-agent 是当前 harness 里的这一类执行者。

- 按任务要用到的能力选：工具、隔离、会话续用、上下文压缩。每一轮工具调用、每一次压缩都增加耗时和出错的机会；材料已备齐、一次判断或生成就够、任务又没有隔离之类的宿主要求时，优先直接调用。
- 已决定用 harness，且当前宿主的原生 sub-agent 满足所需的模型、effort、工作区、权限与隔离时，优先原生派发，少一层跨宿主传参。满足不了、用户点名了另一套组合，或确需在外部并行时，才用外部 harness。

## 读图

换模型或调用路径读图时，先拿一张已知答案、能检验任务所需细节的图试跑，直接调用与 harness 都适用：有的路径会把图转成文本或缩小，模型照样作答、不报错。

## 两条路径怎么比

总 token 数不是成本：缓存读、未缓存输入、输出的单价和耗时各不相同。比较两条可用的路径时，用同一组有代表性的任务和同一质量标准，分别记下未缓存输入、缓存读写、输出、总耗时和无效结果，按各自的实际计价比；耗时按有依赖的轮次和实际并发量。省下的成本只在质量相当时才算数。有可比的免费路径时直接试跑（常驻原则 §3）。

## 批量

先用有代表性的小批核对答案质量、空答与截断的比例和耗时，再定每批大小与并发。
